# Architecture (den wiring)

This repo uses [den](https://github.com/denful/den) (a flake-parts module) for host/user wiring. The core idea: **configuration is organized by feature, and hosts merely pick features** — instead of piling modules onto each host.

## Concepts

| Concept | Meaning | Location in this repo |
|---------|---------|----------------------|
| Entity | A host or a user | `den.hosts.x86_64-linux.<name>` (generated by hosts.nix) |
| Aspect | A feature; may carry both `nixos` and `homeManager` config | `den.aspects.<feature>` (`modules/features/<feature>.nix`, file name = aspect name, directory auto-aggregated) |
| `includes` | Aspect composition: host/user aspects pick features with it | `hostFeatureNames`/`userFeatureNames` in hosts.nix |
| `den.schema` | Typed metadata declarations for entities (typos in host.nix fail fast) | `den.schema.host`/`den.schema.user` in schema.nix |
| `den.default` | Config applied to every entity (external OS modules, overlays, `_module.args`) | defaults.nix |
| class | Config class: `nixos` / `homeManager` | The module files |
| `provides.to-users` | Aspect mounts on the host but delivers its homeManager part to its users | `features/desktop.nix`, `niri.nix`, `mango.nix` |

## Data flow

```
hosts/<name>/host.nix (machine parameters)
        ├─ modules/flake/schema.nix typed metadata (cpu/gpu/disk/primaryUser/proxy, per-user fields)
        └─ modules/flake/hosts.nix
              ├─ den.hosts          host entities + <name>-install variants + user entities
              └─ den.aspects.<name> host aspect: imports hosts/<name>/, picks features via includes
modules/features/<feature>.nix
        └─ den.aspects.<feature>    feature aspect (directory auto-aggregated into flake-parts)
```

- A host aspect binds automatically to the host entity of the same name; same for user aspects and user names.
- HM forwarding: a user entity's `homeManager` class content is written to `home-manager.users.<user>` by den (which also imports the HM NixOS module at that point).
- Parametric modules: modules needing machine parameters use the flat form (`{ host, ... }: ...`, reading `host.cpu` etc.); the user aspect uses `{ user, ... }:`. Flake inputs and `mylib` are the exception, injected via `_module.args` in defaults.nix.

## The install variant

Every host also has a `<name>-install` configuration (stage one of a fresh install via `init.sh`):

| Difference | Implementation |
|-----------|----------------|
| No secrets/flatpak/mango | Derived from `hostFeatureNames` with `installExcludedFeatureNames`; Mango needs the full HM user services, so the installer never exposes a partial session |
| No Home Manager | user `classes = [ "user" ]` (overrides the schema default `homeManager`) |
| No hm-global | referencing `home-manager.*` options without the HM module errors with "option does not exist" |
| Same network name | the entity's `hostName` points back to the regular host name |

Regular hosts include `desktop`, `niri`, and `mango` together. The install variant keeps `desktop` + `niri`, preserving the known-good default Niri session during installation. All three names participate in the shared aspect collision check; no host schema field is added.

## Constraints

- Host names, `<host>-install` names, user names, and feature names share `den.aspects`; the wiring layer counts and rejects collisions.
- Every `primaryUser` must also exist under `users.<name>`; the wiring layer rejects dangling references before configuration generation.
- `cpu`/`gpu`/`disk`/`primaryUser` and user email deliberately have no defaults. `proxy` may be `null`; admin access and SSH keys default to disabled/empty.
